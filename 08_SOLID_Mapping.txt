SOLID MAPPING

1. Single Responsibility Principle (SRP)
Applied to:
- PriceCalculator: only calculates prices.
- TicketPrinter: only formats/prints tickets.
- Payment subclasses: only perform their particular payment method.
- BookingService: coordinates the booking flow instead of performing every individual responsibility.

2. Open/Closed Principle (OCP)
Applied to Payment hierarchy.
To add NetBanking, create:
class NetBankingPayment : public Payment { ... };
Existing BookingService code does not need to know the concrete payment type.

3. Liskov Substitution Principle (LSP)
Applied to Payment.
UpiPayment, CardPayment and CashPayment can all be passed through a Payment& and used through pay(amount) without changing the booking algorithm.

4. Dependency Inversion Principle (DIP)
Applied to BookingService receiving Payment& instead of constructing CardPayment/UpiPayment itself.
The high-level booking flow depends on the Payment abstraction.

5. Interface Segregation Principle (ISP)
The Payment abstraction exposes only the operation required by this assignment: pay(amount).
It does not force every payment class to implement unrelated operations such as refund().

Thing deliberately NOT done:
A separate RefundablePayment interface was not introduced because the assignment only requires payment and cancellation of bookings. Adding refund-related behaviour would unnecessarily expand the current design.
